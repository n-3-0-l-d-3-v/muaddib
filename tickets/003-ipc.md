# 003 — IPC with capability-carrying messages

Message-passing channels between processes where capabilities
themselves are transferable payloads — the classic capability-system
feature that lets authority be delegated at runtime rather than only at
spawn time.

## Scope
- [x] Channel endpoints as capability-guarded objects in their own right
      (`Rights::WRITE` = may send, `Rights::READ` = may receive — the
      first real meaning given to ticket 001's previously-uninterpreted
      rights bits).
- [x] Messages that can carry capabilities (for other objects, or other
      channels) as payload, with `Kernel::derive`'s attenuation rules
      enforced on send — reusing ticket 002's `process::resolve_grants`/
      `apply_transfers` directly rather than a parallel implementation
      (a real discovery made while implementing this ticket: spawning a
      child with attenuated authority and sending a capability over a
      channel are the same operation shape).
- [x] Property test: a capability received over a channel can never
      grant more authority than the sender actually held at send time —
      proven for arbitrary rights combinations
      (`a_received_derived_capability_never_exceeds_what_the_sender_held`)
      and for an arbitrary-length relay chain across multiple channels
      (`a_capability_relayed_through_a_chain_of_channels_is_never_duplicated_or_lost`).

7 unit tests plus 2 property tests, all passing. Also proves a state
worth proving explicitly: a sent-but-not-yet-received capability exists
in *no* process's table at all — not the sender's (already removed on
send), not the receiver's (not yet granted) — only in the channel
registry's own queue
(`an_in_flight_capability_exists_in_no_process_table`).

See `docs/design/decisions/ADR-003-ipc.md` for the channel-rights,
shared-grant-machinery, and in-flight-capability design choices.
